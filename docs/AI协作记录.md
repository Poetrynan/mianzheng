## 二、AI 真正帮到的地方

1. **把证据拉齐**：论文、厂商案例、从业者自述摊在一张表上，按 A/B/C/D 分级；「厂商案例只当线索」这条纪律是它提醒的，后来救了一次（没把 Moka 的 75% 当成自己的调研数据）。
2. **把流程变成可点的原型**：三个功能、两清单、同意/审计/闸门；很多判断是点进去才发现的（一页纸必须一屏看完、同意与拒绝要同等权重）。
3. **Agent 运行时**：循环、步数预算、重复保护、暂停恢复、持久化、审计；引用核对与人工闸门交给确定性代码。
4. **负样本思路**：只测「找得到」的绿色是假的，必须准备「确实没有原话」的样例，确认它标缺口而不是编。
5. **可验证的检查**：对比度脚本、视觉溢出探测、线上链路验证——把「我觉得」变成能跑的命令。
6. **结构化文档**：PRD 的章节骨架、指标公式、验收清单；但每一句都要拿代码和线上行为复核。

## 三、AI 看似合理、其实站不住的建议

| 建议 | 为什么听起来对 | 怎么发现 | 怎么改 |
|---|---|---|---|
| 整个应用放 Vercel | Vercel 能跑 Node 函数 | 读自己的存储实现：会话与面评都在 SQLite，函数实例之间不共享 | 静态页 + 转发 + Render 持久后端 |
| 雷达图连满所有维度 | 「一眼看整体形状」 | 真实数据：零原话仍是满五边形 | 只连有原话的维度；空心圈不进形状 |
| 这屏给用人经理 | 决定录用的是他 | 角色表：他每岗只登录一次 | 改归 HR；写清 V1 边界 |
| 演示数据一个满分候选人 | 整齐、稳定 | 打开没有对比、没有缺口 | seed 三人三态，看板 1/2 |
| 每个分必须挂原话 | 这是产品最响的口号 | 代码允许无原话终评，只是标空心、不算可用 | 改成「结论要能回到原话；缺口留明面」 |
| AI 不给分 | 原则是人不被替代 | 草稿里 AI 确实起评分，只是矩阵不认 | 改成「AI 只起草，分数由人定」 |
| 照 4:30 逐字稿录 | 稿子写得完整 | 作业要求 3 分钟、出镜、不念稿 | 重写成提纲与判断链 |
| 装 `to-prd` | 搜索结果显示安装量最高 | 安装时仓库已无此技能 | 改用官方 `prd-writer`，并把模板默认口径按代码改正 |

## 四、我怎么识别与修正

**四问**：谁在什么时刻用它？它替代了什么？如果是错的，现场会看到什么？做完哪个数会变？
**一跑**：用真实数据/真实流程跑一遍，看它在不该好看的时候好不好看（负样本、真实转写、真实权限）。
**落点**：每条修正都要留下可验证的痕迹——一条测试、一个脚本、一个线上请求、一个 commit，而不是一段更漂亮的解释。

三个具体手法：
- **读自己的代码**：PRD 里「没推荐不能提交」就是被 `requirementsForSubmit` 打掉的；
- **读自己的角色表**：用人经理只登录一次，是把我「给经理看」的判断打掉的；
- **跑真实数据**：雷达满格、演示满分、看板 1/1，都是跑出来才露馅的。
